# PR description 작성 + PR 생성

현재 브랜치의 **커밋된** 변경을 분석해 팀 PR 템플릿을 채운 마크다운을 만들고, 사용자와 확정한 뒤 **`gh pr create`로 PR 생성까지 한다**(기본 base: main).

이 스킬의 목적은 리뷰어가 diff를 열지 않고도 "무엇을·왜·배포 시 뭘 주의해야 하는지"를 이해하게 만드는 것. 그래서 diff를 나열하는 게 아니라 **도메인 맥락**으로 번역하고, 체크리스트는 추측이 아니라 diff 근거로 채운다.

## 워크플로

### 1. base 브랜치 확정

PR이 머지될 대상(base)을 정한다. 순서대로:

```bash
git branch --show-current
git branch -r | grep -E "origin/(main|develop|master)$"
# 각 후보에 대해 HEAD가 몇 커밋 앞선지 (가까운 쪽이 base 후보)
git rev-list --count origin/main..HEAD
git rev-list --count origin/develop..HEAD
```

- 후보가 하나뿐이거나 명확히 가까운 쪽이 있으면 그걸 base로 쓴다.
- **main과 develop이 동일하게 앞서 있거나(분기점이 같음) 애매하면 사용자에게 base를 확인**한다. 잘못된 base로 diff를 뜨면 엉뚱한 변경이 섞이므로 여기서 추측하지 말 것.

**엣지 케이스 — HEAD가 base 대비 0커밋:** `git rev-list --count BASE..HEAD`가 0이면(현재 브랜치가 base upstream과 동일, 예: `develop`이 `origin/develop`과 같음) "이 PR의 변경"이라는 개념이 성립하지 않는다. 다른 후보를 base로 재검토하거나, 그래도 0이면 **멈추고 사용자에게 "어떤 브랜치를 어디로 머지하는 PR인지" 확인**한다. 억지로 먼 base(예: develop인데 main)를 골라 수백 커밋짜리 diff를 뜨지 말 것 — PR 범위가 아니다. 이때 미커밋/untracked 작업물이 있으면(`git status --short`) "이 변경을 feature 브랜치에 커밋한 뒤 다시 실행하면 그 브랜치 기준으로 작성해 드린다"고 다음 액션을 함께 제안한다.

이하 `BASE`는 확정된 base 브랜치.

### 2. 커밋된 변경만 분석 (미커밋 제외)

PR에는 커밋된 것만 올라간다. 미커밋/untracked 파일은 **description에 넣지 않는다.**

```bash
git diff BASE...HEAD --stat              # 변경 파일 개요
git log BASE..HEAD --oneline --no-merges # 커밋 목록 (작업 단위 파악)
git diff BASE...HEAD -- <핵심파일>        # 로직 변경 실제 내용
```

**머지 커밋 처리:** `--no-merges`로 머지 커밋을 걸러 실제 작업 커밋만 본다. release/feature 브랜치가 섞인 로그에서 머지 커밋은 작업 단위가 아니므로 무시한다. 작업 단위는 커밋 메시지가 아니라 **`--stat`의 파일 묶음**으로 판별하는 게 더 정확하다 — 같은 도메인·기능의 파일들을 하나의 `###` 소제목으로 묶는다.

미커밋 파일이 있으면(`git status --short`) description에서 제외하되, 응답 말미에 "미커밋 X는 이 PR 미포함"이라고 한 줄로 짚어준다. 사용자가 놓치지 않도록.

### 3. 체크리스트 근거를 diff로 판단

각 항목을 추측하지 말고 diff로 확인해 근거와 함께 채운다:

| 체크리스트 항목 | 판단 방법 |
|---|---|
| 기능 정상 동작 확인 | 관련 테스트 실행(레포 러너 기준, 예: `poetry run pytest <관련 테스트>`) → 통과 수. 테스트가 없는 repo면 수동 검증 방법을 명시 |
| DB 마이그레이션 필요 여부 | diff에 `alembic/`, `*/migrations/`, `*/versions/`, model/schema 파일 변경 있나 |
| 설정 파일 변경 여부 | `*settings*`, `*.cfg`, `*.toml`, `*.env*` 변경. 버전 bump(1~2줄)뿐이면 "버전 bump만"으로 명시 |
| 배포 순서/추가 작업 | 마이그레이션 선행·환경변수 신규·플래그 토글 등 있으면 순서 기술. 없으면 "배포만 하면 됨" |
| 테스트 작성 및 통과 | `tests/` diff에 신규/변경 테스트 있나 + 실제 통과 |

**외부 서비스 동시 배포 의존성**도 확인한다. 같은 플랫폼의 서비스들은 서로의 API 계약을 참조한다. 응답 필드·엔드포인트 시그니처를 바꿨다면 그 소비자 서비스도 함께 배포해야 하는지 짚는다. 외부 호출 클라이언트(`*/services/`, `app/**/service/` 등)와 라우터 응답 모델 변경을 확인한다. (인프라·설정 repo처럼 해당 없으면 생략.)

### 4. 도메인 정정 루프 (중요)

diff만으로는 **왜** 이렇게 바꿨는지 정확히 못 쓴다. 초안의 "배경/변경 이유"는 코드에서 추론한 가설이므로, 사용자가 정정할 여지가 크다. 초안을 낸 뒤 사용자 피드백을 받아 **배경 문단을 우선 고친다.** 한 번에 맞추려 하지 말고, 사용자가 도메인 사실을 주면 그대로 반영해 다시 낸다. 이 루프가 이 스킬의 핵심 가치다.

### 5. PR 생성 (확정 후)

초안을 제시할 때 "이대로 PR 올릴까요?"를 함께 묻고, 사용자가 확정하면 PR을 올린다. **확정 전에 임의로 올리지 않는다.**

```bash
git push origin HEAD                                    # 브랜치가 origin에 없거나 뒤처졌으면 먼저 push
gh pr create --base main --title "<제목>" --body "<확정된 description>"
```

- **base는 main 기본.** 사용자가 다른 base를 지시하면 그걸로, repo에 main이 없으면 master.
- **title** 형식: `<emoji> <TAG>: <제목> (v<릴리즈버전>)` — 예: `✨ FEAT: 사업주 훈련 EMON 연동 정비 (v1.12.6)`. 제목은 브랜치 변경을 한 줄 요약(커밋 컨벤션과 동일).
  - 릴리즈버전은 HEAD의 버전 파일에서 읽는다: `pyproject.toml`의 `version` → `.bumpversion.cfg`의 `current_version` → `setup.cfg` 순. PR에 버전 bump가 포함돼 있으면 bump된(새) 버전을 쓴다.
  - **컴포넌트별 버전 repo**(`.bumpversion.<컴포넌트>.cfg`가 여러 개, 예: home/backoffice/scheduler): 단일 `(vX.Y.Z)` 대신 **이 PR의 diff에서 bump된 컴포넌트만** `이름 v버전`으로 나열한다 — 예: `✨ FEAT: 지원서 검색 개선 (home v0.0.7, backoffice v0.0.6)`. diff에 bump가 하나도 없으면 어느 컴포넌트 릴리즈인지 추측하지 말고 사용자에게 확인(모르면 버전 생략).
  - 버전 파일이 없는 repo(인프라·설정 등)는 `(v...)`를 생략한다.
- 같은 브랜치의 열린 PR이 이미 있으면(`gh pr list --head $(git branch --show-current)`) 새로 만들지 않고 `gh pr edit --body`로 본문만 갱신한다.
- 생성/갱신 후 **PR URL을 보고**한다.

## 출력 형식

아래 골격을 쓴다 — **이 스킬이 유일한 템플릿 소스**다(repo에 별도 `.github/PULL_REQUEST_TEMPLATE.md`를 두지 않는다). 항상 **복붙 가능한 코드블록 하나**로 출력한다(사용자가 통째로 붙여넣게).

```markdown
## 🛠️ 작업 내용

### <작업 단위 제목>

**배경**
<왜 이 작업이 필요했는지. 모르는 사람도 이해하도록 도메인 용어를 풀어서. 코드 심볼(플래그/함수명)은 백틱으로.>

**변경 내용**
- <기존이 어땠고 → 무엇으로 바꿨는지>
- <핵심 심볼의 역할을 한 줄씩>
- **현재 값/설정**: <운영에 실제 적용되는 값과 그 이유>   ← 정책·설정 변경일 때만

**앞으로 <조건>이 바뀌면**   ← 이 소제목은 PR마다 달라짐(선택). 후속 조치/전환 조건이 있을 때만.
- <다음에 뭘 해야 하는지, 전환 조건>

### <다른 작업 단위>
- <...>

### 기타
- <테스트 보강, 버전 bump 등>

## ✅ 체크리스트
- [x] 기능 정상 동작 확인 (<근거: 테스트 N개 통과 등>)
- [x] DB 마이그레이션 필요 여부 — <불필요 / 필요 시 내용>
- [x] 설정 파일 변경 여부 — <버전 bump만 / 없음 / 내용>
- [x] 배포 순서 또는 추가 작업 필요 여부 — <없음 / 순서 기술>
- [x] 신규/변경된 기능에 대한 테스트 작성 및 통과
```

### 형식 규칙

- **작업 내용**: `###` 소제목으로 작업 단위를 나눈다. 각 소제목 밑의 **배경 / 변경 내용 / 앞으로...** 구조는 고정이 아니라 그 작업에 맞게 쓴다. 단순 변경이면 불릿 몇 개로 충분하고, 정책·로직 변경처럼 맥락 설명이 필요하면 배경 문단을 붙인다.
- **체크리스트**: 템플릿 5개 항목 순서·문구 유지. 확인한 항목만 `[x]`, 각 항목에 판단 근거를 `—` 뒤에 짧게 붙인다.
- **언어**: 한국어. 리뷰어가 도메인을 몰라도 이해하게. 다만 코드 심볼(플래그·함수·파일명)은 정확히 백틱으로.
- **길이**: 배경은 3~5문장이면 충분. 장황하게 늘리지 말 것.

## 예시

**Input:** (feature 브랜치, 강의 콘텐츠 관련 커밋 존재) "PR 메시지 작성해줘"

**Output (발췌):**

```markdown
## 🛠️ 작업 내용

### 강의 챕터 정렬 순서를 수동 지정 가능하도록 변경

**배경**
기존에는 강의 챕터가 생성 시각순으로만 노출돼, 운영자가 커리큘럼 순서를 바꾸려면 챕터를 지우고 다시 만들어야 했습니다. 운영자가 순서를 직접 지정할 수 있도록 정렬 필드를 추가했습니다.

**변경 내용**
- `Chapter` 모델에 `display_order` 컬럼 추가, 조회 시 `display_order` 오름차순 정렬
- 챕터 정렬 변경 admin 엔드포인트(`PATCH .../chapters/reorder`) 추가
- 기존 챕터는 마이그레이션에서 생성 순서대로 `display_order` 백필

## ✅ 체크리스트
- [x] 기능 정상 동작 확인 (챕터 정렬 관련 테스트 통과)
- [x] DB 마이그레이션 필요 여부 — 필요 (`display_order` 컬럼 추가 + 기존 데이터 백필). 배포 시 마이그레이션 선행
- [x] 설정 파일 변경 여부 — 없음
- [x] 배포 순서 또는 추가 작업 필요 여부 — 마이그레이션 먼저 적용 후 앱 배포
- [x] 신규/변경된 기능에 대한 테스트 작성 및 통과
```
